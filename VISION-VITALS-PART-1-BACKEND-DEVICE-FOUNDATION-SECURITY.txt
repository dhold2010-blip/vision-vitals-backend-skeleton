2. PRIMARY OBJECTIVE

Add the backend foundation required for a physical Vision Vitals device.

Hardware:

* Raspberry Pi Zero 2 W
* Raspberry Pi Camera Module 3 Wide
* optional VL53L0X distance sensor
* controlled LED illumination

The Raspberry Pi is an INPUT DEVICE.

The Raspberry Pi is NOT:

* the backend
* the database
* the AI engine
* the authority for user identity
* the authority for ownership
* the authority for health results

The backend remains the security boundary.

5. DEVICE OWNERSHIP

Every device belongs to a user.

The SERVER-SIDE authenticated user is authoritative.

NEVER trust from a device request:

* owner_user_id
* user_id
* role
* permissions

A device request must derive identity from the authenticated device credential/session and the server-side device record.

Implement strict ownership checks.

User A must NEVER be able to:

* access User B’s device
* capture through User B’s device
* submit sensor readings for User B’s device
* modify User B’s device
* revoke User B’s device
* retrieve User B’s device information

Protect against IDOR/BOLA vulnerabilities.

⸻

6. DEVICE AUTHENTICATION

Implement secure device authentication.

Do NOT authenticate solely with:

device_id

A device must possess a secret credential.

The backend should identify:

device
+
authenticated device credential/session

Do not store raw device secrets if avoidable.

Store a securely derived/hashed representation.

Never hard-code device secrets.

Never commit device credentials.

Never put secrets in source code.

Never expose device secrets through API responses.

⸻

7. DEVICE SESSION

If DeviceSession already exists, extend it.

Otherwise create it.

Conceptually support:

device_id
session_identifier
created_at
expires_at
revoked_at
last_seen_at

A revoked session must immediately become invalid.

An expired session must be rejected.

Do not use ordinary user JWTs as a substitute for proper device authentication unless the existing architecture already provides a secure device-specific mechanism.

Follow existing security conventions where appropriate.

⸻

8. DEVICE REGISTRATION

Implement secure device registration.

Use the existing authenticated user system.

A normal authenticated user should be able to register/pair a device.

Do not allow an unauthenticated client to arbitrarily register devices to another user.

Do not allow a device to claim ownership by submitting:

“user_id”

or:

“owner_user_id”

The server determines ownership.

If the existing architecture has a pairing mechanism, extend it.

If it does not, implement a secure registration flow appropriate for the existing application.

Never return long-term secrets unnecessarily.

⸻

9. DEVICE CREDENTIAL ROTATION

Implement credential rotation.

Requirements:

* old credential becomes invalid when rotation completes
* new credential is generated securely
* credential is never logged
* credential is never stored in plaintext when avoidable
* credential is never returned unnecessarily
* revoked devices cannot rotate credentials
* unauthorized users cannot rotate credentials

⸻

10. DEVICE REVOCATION

Implement device revocation.

Revocation must invalidate active device sessions.

A revoked device must not be able to:

* authenticate
* heartbeat
* upload captures
* submit sensor readings

until explicitly re-registered according to the security model.

Do not simply mark a device revoked while continuing to accept existing sessions.

⸻
